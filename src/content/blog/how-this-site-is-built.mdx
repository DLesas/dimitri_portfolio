## What I wanted from it

I rebuilt this site with four goals, in this order. It had to be **fast on any device**, including a mid-range phone on a train. It had to be **cheap enough to forget about**: the AWS side averages around twenty cents a month. It had to be **safe to leave running**, with no keys stored anywhere and hard caps on anything that costs money. And it needed one thing that is simply fun to play with: the network of nodes behind every page, which you can push around with your cursor, along with everyone else who happens to be reading.

Each goal ended up deciding something concrete. This post walks through those decisions, roughly from the browser outwards. Here is the whole of it: pick a flow to follow it through, point at a part to see what it does, or drag to turn it.

## Server first, 3D after

Pages are React Server Components on Next.js 16, so the text you are reading arrived as plain HTML. The entrance animations are CSS rather than JavaScript, which means they start playing before React has even loaded. The 3D network loads in its own chunk, once the browser is idle after the first paint, so it never competes with the text for the network or the main thread.

### The network in four draw calls

However many nodes are on screen, the background is drawn in four draw calls: other visitors' cursor glows, your own cursor glow, every connection, and every node. Nodes live in typed arrays rather than as objects, and connections are drawn as instanced quads whose width and opacity fade with distance. Nothing in the render loop allocates memory, so there are no garbage-collection pauses mid-animation.

### Physics at a fixed 60 Hz

The movement constants were tuned per 60 Hz frame. On a 120 Hz screen, or when the browser drops frames, stepping once per animation frame would change how the whole thing feels. So the simulation keeps its own clock and steps in fixed increments:

```ts
// Catch up in fixed 1/60 s steps, at most four per frame
acc = Math.min(acc + delta, STEP * MAX_STEPS_PER_FRAME);
while (acc >= STEP) {
  physicsStep(inputs, mouse, remotes, colliders);
  acc -= STEP;
}
```

Each node wanders on a path of its own, made from two slow waves per axis at rates that never line up, so no node ever traces a loop or moves in step with its neighbours.

### Finding connections with a grid

Every update, each node needs to know which others are close enough to link to. Comparing every pair is 19,900 checks for 200 nodes. Instead, nodes are dropped into a grid of cells one link-distance wide, and each node is only compared with its own cell and the eight around it: about 1,600 checks. Links that already exist keep their place until they fade out, and the closest remaining pairs fill the rest.

## Live cursors

If someone else is reading this page right now, their cursor shows up as a soft glow, labelled with an animal name and their rough location, and it pushes the network around exactly like yours does.

### One channel, mostly quiet

Cursors travel over a single AWS AppSync Events channel, using four message types: `hi`, `mv`, `out` and `bye`. A visitor announces itself on arrival, sends moves while its cursor is over the page and says goodbye on the way out. While other people are around, a heartbeat every 20 seconds keeps you listed; alone, it drops to every two minutes, which cut presence traffic by about 92% for the most common case: one person reading on their own.

### Every message is rebuilt

The browser publishes with a public API key, so anyone could try to push anything through the channel. The channel's handler only rebroadcasts well-formed cursor messages, and it rebuilds each one from the fields it knows rather than passing the original along:

```js
function clean(m) {
  const out = { v: 1, id: m.id, t: m.t, c: m.c };
  if (m.t === "mv") { out.x = m.x; out.y = m.y; }
  return out; // anything else in m is dropped
}
```

## Keeping the bill near zero

Real-time features are the part of a hobby site most likely to produce a surprise bill, so the cursors are built to switch themselves off before that can happen.

### A hard spending cutoff

A small Lambda function deletes the AppSync API keys, which switches live cursors off for everyone, in three situations: when a per-minute alarm trips on message, connection or subscription counts; when a check every 15 minutes finds the month's AppSync spend past $2; or when an AWS Budgets alert fires as a backstop. Turning cursors back on is a deliberate, manual step.

<Callout>
The worst realistic case is a slow drain that stays under every per-minute alarm. Even that stops at the monthly check, a few dollars in.
</Callout>

### The contact form

Messages go out through Amazon SES using a role that Vercel assumes over OIDC, so there is no AWS key stored anywhere. That role only works from production, and it can only send email to my own inbox. Each visitor can send five messages a day, counted in DynamoDB, and a firewall rule allows five requests per IP every ten minutes on top of that.

## Infrastructure as code

Everything outside Vercel is described in Pulumi, in TypeScript: the AppSync API and its handler, the alarms and the cutoff function, SES and its DNS records, and the DNS zone itself on Cloudflare. Nothing is configured by hand in a console, so the whole setup can be read, reviewed and rebuilt.

### Previews on every pull request

GitHub Actions runs a Pulumi preview on every pull request, so the infrastructure diff sits next to the code diff, and deploys when the change merges to `main`. Actions are pinned to full commit SHAs, and secrets are scoped to the single step that needs each one.
